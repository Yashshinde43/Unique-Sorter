Phase 2 — Next Up

Inventory Management + Sales Invoice + Delivery

Phase 2 extends the existing pipeline. Currently the flow stops at quotation. Phase 2 takes it further: Enquiry → Quotation → Sale → Invoice → Machine Booked → Delivery. It also adds inventory tracking for machines in the godown (warehouse).

1 Sales Invoice — Generate sale invoice after quotation converts to sale
2 Inventory System — Track machines in godown with serial numbers
3 Machine Booking — When sold, machine gets booked to customer with delivery date
4 Multiple User Roles — Warehouse manager, owners with different access
💰

Phase 2 — Part 1: Sales Invoice

Quotation → Sale → Invoice
Currently the system only generates quotations. Phase 2 adds the next step: when a quotation converts to a sale, the system generates a sales invoice. This completes the pipeline from enquiry to revenue.
Discussed: "Abhi tak sirf quotation generate ho raha hai aur quotation apan send kar rahe hain. Basically ab sale ka invoice aur delivery wala jo hai woh Phase 2 hai."
Pipeline Extension
The full pipeline after Phase 2 will be:
Enquiry → Quotation → Sale → Invoice → Machine Booked → Delivery

Phase 1 covers Enquiry → Quotation. Phase 2 covers Sale → Invoice → Machine Booked → Delivery.
📦

Phase 2 — Part 2: Inventory Management

Machine Tracking in Godown (Warehouse)
Machines sitting in the godown need to be tracked. Each machine has a serial number, model name, and availability status. The inventory system shows what's available, what's booked, and what's been delivered.
Discussed: "Inke jo godown mein machines rakhi hain, unka serial number ho gaya, machine ho gayi — toh for example 10 machines. Inventory system mein dikhna chahiye."
Machine Booking on Sale
When an enquiry converts to a quotation and then to a sale, a specific machine from inventory gets booked to that customer. The system should show:
• Which machine is booked to which customer
• Whether the machine is new/available or already booked
• Delivery date for the booked machine
Discussed: "Woh sale ho gaya, toh woh machine — book ho gaya. Falana falana insaan ke naam book ho gaya. Toh usko dikhna chahiye inventory system mein ki bhai ye machine naya hai already aur iska delivery date falana falana hai."
Linked to Existing Pipeline
Inventory is not a standalone system. It is directly linked to the CRM pipeline. When a sale happens through the CRM (enquiry → quotation → sale), the inventory automatically updates. No separate data entry.
Key Point: "Phase 2 hai only inventory — woh bhi isi se linked inventory, isi ka aage pipeline."
👥

Phase 3 — Future

Mobile App (Android + iOS)

Phase 3 adds a mobile application that connects to the same Firebase backend. The web CRM continues to work as-is — the mobile app is an additional frontend. Built with Flutter for both Android and iOS.

1 Flutter App — Single codebase for Android + iOS
2 Same Backend — Firebase backend shared with web CRM
3 UI Only Change — Only the frontend/UI changes, backend stays the same
4 Store Publishing — Separate charges for Google Play / App Store
📱

Phase 3 — Technical Approach

Flutter for Mobile — React Stays for Web
The current web CRM uses React (Next.js). The mobile app will use Flutter which builds for both Android and iOS from a single codebase. The web version stays on React — no migration needed.
Decided: "Web mein React rahega aur Android mein Flutter. Flutter mostly. Haan Flutter hi rahega, koi dikkat nahi hai."
Same Firebase Backend — UI Swap Only
The Firebase backend serves both web and mobile. Multiple frontends, one backend. Web UI, Android app, and iOS app all interact with the same Firebase project. No separate hosting or backend needed for mobile.
Decided: "Backend Firebase mein hai. Toh nahi, alag karna padega. Ek rakh liye web UI, ek rakh liye Android, ek rakh liye iOS — ek hi backend se interact karega."
Backend Readiness
While working on Phase 1 and 2, the backend should be kept mobile-ready. Since the web APIs are already built, the mobile app mostly needs a UI layer on top. No major backend rework expected.
Discussed: "Agar inke kaam nahi aata toh tumhara mobile app ke liye backend ready rahe. Web API ready hai toh mobile ke liye bahut zyada tension nahi lagega."
🏫

Phase 3 — App Distribution & Publishing

APK Install vs Store Publishing
Two options for distributing the app:

Option A — APK File (Simple): We give them the APK file, they install directly on their phones. No store listing, no review process.

Option B — Google Play / App Store (Separate Charges): Publish to Google Play Store and/or Apple App Store. This involves a review process, 5-10 testers requirement, and additional charges beyond the Phase 3 fee.
Important: "Hum aapko app de denge, aap install kar lo APK file se. Publish karna hai toh uske phir charges alag rahenge. Publishing aaj kal aasan nahi hai — 5-10 testers se kuch system rehta hai."
Android + iOS Confirmation Needed
Need to confirm with the client whether they want:
• Android only
• iOS only
• Both Android + iOS

Flutter supports both from a single codebase, but store publishing costs and effort differ.
Discussed: "Unse ye bhi confirm karna padega ki Android ke liye bhi rakhna hai ya sirf iOS ke liye. Dono ke liye rakhna hai?"
Phase 3 Pricing Will Be Separate
Phase 3 (mobile app) will not be priced at ₹1 lakh like Phase 2. The pricing will be discussed separately when the time comes. Store publishing charges are on top of the app development cost.
Discussed: "Phase 3 jab bhi hoga toh lakh mein toh nahi hoga. Publish karna hai toh charges alag."
